# Техническое задание: UniChat — многофункциональный чат-плагин для Paper (с прицелом на порт на Spigot/Bukkit/Folia)

Версия документа: 1.0
Аудитория: AI-модель (Sonnet 5) в роли разработчика плагина
Статус: черновик к разработке, дополняется по ходу работы

---

## 1. Цель и концепция проекта

Разработать современный, производительный и гибко настраиваемый плагин чата для серверов Minecraft на ядре **Paper** (в дальнейшем — с возможностью портирования на **Spigot/Bukkit** и **Folia**), закрывающий нишу отсутствия качественных актуальных чат-плагинов под новые версии игры.

Плагин должен:

- Полноценно интегрироваться с **LuckPerms** (права, префиксы/суффиксы, meta-данные) и **Vault** (экономика, легаси-права как fallback).
- Поддерживать раздельные **каналы чата**: Глобальный, Локальный, Торговый, Личные сообщения (ЛС) — все опциональны (можно отключить любой).
- Позволять администраторам и (опционально) самим игрокам настраивать **цвет префикса, цвет никнейма и цвет текста сообщения** отдельно друг от друга.
- Помечать сообщения **метками канала**: `[G]`, `[L]`, `[$]`, `[ЛС]` (тексты и цвета меток настраиваемые).
- Иметь настраиваемый **радиус локального чата** (по умолчанию — **200 блоков**).
- Вобрать лучшие функции конкурентов (ChatControl, VentureChat, DeluxeChat, EssentialsX Chat, TownyChat) — расширенное форматирование, модерация, антиспам, приватные каналы, JSON hover/click, упоминания и т.д.

## 2. Целевая среда выполнения

- **Приоритет разработки:** Paper, версии **1.20.x – актуальная (1.21+)**, Java 21+.
- **Дальняя перспектива (не блокирует MVP, но должна закладываться архитектурно):** порт на Spigot/Bukkit (для серверов без Paper) и адаптация под **Folia** (регионально-поточная модель).
- Из этого следует **архитектурное требование**: максимально изолировать Paper-специфичный код (Adventure API, `AsyncChatEvent`, Brigadier-команды, Folia-scheduler) за собственными интерфейсами/абстракциями, чтобы в будущем заменить реализацию под Spigot без переписывания бизнес-логики. Это не должно тормозить реализацию фич сейчас — просто не захардкоживать Paper-only вызовы в бизнес-логике каналов, цветов и модерации напрямую, а проводить через сервисный слой (см. раздел 4).

## 3. Технологический стек

- **Язык:** Java 21 (records, sealed classes, pattern matching — уместны для моделей каналов/событий).
- **Сборка:** Gradle (Kotlin DSL), плагин `com.gradleup.shadow` (или `com.github.johnrengelman.shadow`) для релокейта шейдед-зависимостей (Kotlin не нужен, если не используем; HikariCP, Configurate и т.п. — релоцировать).
- **API:** `paper-api` (последняя стабильная версия) как `compileOnly`; **Adventure API** (входит в Paper) для всего текста и цвета — `Component`, `MiniMessage`, никакого legacy `ChatColor` в новом коде (кроме слоя обратной совместимости с легаси `&`-кодами при парсинге пользовательского ввода).
- **Конфиги:** YAML. Рекомендуется библиотека, сохраняющая комментарии при пересборке (`Configurate` 4.x с YAML-загрузчиком, либо `boosted-yaml`), т.к. администраторы правят конфиги руками, а плагин должен уметь домигрировать новые ключи без потери комментариев/структуры.
- **Хранение данных:** по умолчанию — YAML/JSON-файлы (`playerdata/<uuid>.yml`); опционально — SQLite (по умолчанию, если включена БД, но не настроен MySQL) и MySQL через HikariCP (для мутов, истории чата, кросс-сервер готовности в будущем).
- **Мягкие зависимости (soft-depend):** LuckPerms, Vault, PlaceholderAPI, WorldGuard, DiscordSRV. Отсутствие любой из них **не должно ломать запуск плагина** — соответствующий функционал просто деградирует до базового (см. раздел 5).

## 5. Интеграции с другими плагинами

### 5.1 LuckPerms (приоритетная интеграция)

- Использовать **LuckPerms API** напрямую (не только через PlaceholderAPI) для производительности и реактивности.
- Считывать `prefix` и `suffix` из LuckPerms для формата сообщений (плейсхолдеры `%luckperms_prefix%` как fallback-путь через PAPI, но основной путь — прямой вызов API).
- Ввести **собственные meta-ключи LuckPerms**, которые администратор может назначать группам/пользователям без команд плагина:
  - `unichat-prefix-color`
  - `unichat-name-color`
  - `unichat-message-color`
  - `unichat-local-radius` (переопределение радиуса локального чата для группы, например VIP видит на 400 блоков)
  - `unichat-chat-color-hex` (bool/permission-подобный флаг доступа к HEX/градиенту — либо реализовать через обычные permission-ноды, что предпочтительнее для консистентности, см. 5.1.1)
- Подписаться на событие изменения данных пользователя в LuckPerms (`UserDataRecalculateEvent` / `NodeMutateEvent`) и **пересчитывать формат чата у онлайн-игрока без релога**.
- Если LuckPerms не установлен — плагин должен работать на собственной системе цветов (permissions-based, см. раздел 8) без ошибок в консоли (только один информативный INFO-лог при старте о том, что LuckPerms не найден).

### 5.2 Vault

- **Vault Permission** — fallback-источник префикса/суффикса, если LuckPerms API недоступен (сервер использует PermissionsEx/GroupManager и т.п.).
- **Vault Economy** — для функций Торгового чата:
  - Опциональная плата за отправку сообщения в Trade-канал (`trade.message-cost`, по умолчанию 0 — выключено).
  - Подсветка числовых цен в формате `100$`/`100 монет` в тексте объявления (регулярка + Vault currency name).
  - Плейсхолдер баланса игрока в hover-подсказке над его именем в торговом чате (опционально).
- Отсутствие Vault → все экономические фичи тихо отключаются, остальной функционал работает.

### 5.3 PlaceholderAPI

- Зарегистрировать собственный **PlaceholderExpansion** с плейсхолдерами:
  - `%unichat_channel%` — текущий активный канал игрока
  - `%unichat_channel_tag_<id>%` — метка конкретного канала
  - `%unichat_prefix_color%`, `%unichat_name_color%`, `%unichat_message_color%`
  - `%unichat_local_radius%`
  - `%unichat_muted%`, `%unichat_ignoring_count%`
- Формат сообщений (`format` в `channels.yml`) должен поддерживать плейсхолдеры **сторонних** экспаншенов PlaceholderAPI (парсить через `PlaceholderAPI.setPlaceholders(player, template)`), чтобы админ мог вставить `%vault_eco_balance%`, `%luckperms_prefix%`, ранги фракций и т.д. без правки кода плагина.
- Отсутствие PAPI → сторонние плейсхолдеры в форматах просто не разворачиваются (остаются как есть или заменяются на пустоту — решить конфигом `placeholder-fallback: strip|keep`).

### 5.4 Прочие интеграции (не блокируют MVP, но заложить крючки)

- **WorldGuard** — региональные флаги для запрета/разрешения конкретных каналов в регионе (например, отключить локальный чат в мини-игровой арене). Реализовать как отдельный опциональный модуль.
- **DiscordSRV / собственный webhook** — трансляция глобального/локального/торгового чата в Discord и обратно. Phase 4, за флагом в конфиге.
- **EssentialsX** — не конфликтовать с его `/msg`/`/ignore`/mute, дать возможность полностью заменить эти команды плагином UniChat (конфиг-флаг «отключить встроенные команды Essentials через `commands.yml` override» — задокументировать в README, не в коде).

## 6. Система каналов чата

### 6.1 Общая модель канала

Каждый канал описывается в `channels.yml` и имеет как минимум:

```yaml
channels:
  global:
    enabled: true                       # можно полностью выключить канал
    display-name: "Глобальный"
    tag: "&8[&aG&8]"                    # метка перед сообщением
    format: "<tag> <prefix_color><prefix></prefix_color> <name_color><player></name_color><gray>:</gray> <message_color><message></message_color>"
    default: true                       # канал по умолчанию для новых игроков
    range: 0                            # 0 = без ограничения дистанции
    cooldown-seconds: 0
    permission:
      speak: null                       # null = всем, либо unichat.channel.global.speak
      see: null
    shortcut: "!"                       # можно писать "!привет" из любого канала
```

### 6.2 Глобальный чат `[G]`

- Видно всем игрокам сервера (с учётом `ignore`/vanish/мутов).
- Включен по умолчанию, служит fallback-каналом, если остальные отключены.

### 6.3 Локальный чат `[L]`

- Видно только игрокам в радиусе `range` блоков **и в том же мире**.
- **Радиус по умолчанию — 200 блоков**, настраивается в `channels.yml` (`local.range`).
- Дополнительно:
  - Возможность переопределить радиус для группы через LuckPerms meta `unichat-local-radius` или permission-ноду `unichat.local.range.<число>`.
  - Настройка учёта вертикальной дистанции: `local.vertical-check: true|false` (по умолчанию `true` — 3D-дистанция; при `false` считается только горизонтальная 2D-дистанция, что удобно для серверов с большими вертикальными постройками/шахтами).
  - Оптимизация: расчёт получателей не должен быть наивным `O(n)` по всем игрокам сервера при каждом сообщении без кеша на больших серверах — использовать `World#getNearbyEntities`/чанковые выборки Paper API, либо периодически обновляемый spatial-индекс, если игроков много (>200 онлайн). Заложить это как нефункциональное требование (раздел 16).

### 6.4 Торговый чат `[$]`

- По умолчанию — серверный (range: 0), т.к. торговля обычно ведётся между всеми онлайн-игроками.
- Особенности:
  - Cooldown выше, чем у глобального, по умолчанию (борьба со спамом объявлений, частая проблема у торговых чатов).
  - Подсветка цен (регулярка на числа + суффикс валюты) в тексте сообщения отдельным цветом (`trade.price-color`).
  - Опциональная плата за сообщение через Vault (см. 5.2).
  - Клик по имени автора объявления → открывает `/msg <player> ` с подставленным именем (JSON click-event, см. 12.1).

### 6.5 Личные сообщения (ЛС) `[ЛС]`

- Команды: `/msg`, `/tell`, `/w` (алиасы) `<player> <message>`; `/r`/`/reply` — ответ последнему собеседнику; история последнего собеседника хранится в `PlayerDataStore`.
- `/ignore <player>` / `/unignore <player>` — игнорирование ЛС (и опционально всех каналов) от конкретного игрока.
- `/socialspy` (право `unichat.socialspy`) — стафф видит все ЛС на сервере с меткой `[Spy]`.
- Опционально (Phase 3+): офлайн-очередь сообщений («почта») — «игрок увидит сообщение при следующем входе», через `unichat.mail`.

### 6.6 Произвольные пользовательские каналы

- Архитектура каналов не должна быть жёстко ограничена четырьмя типами — админ может добавить в `channels.yml` дополнительный канал (например `staff`, `rp`, `event`) с собственной меткой, форматом, правами и (опционально) радиусом. Тип `CUSTOM` в `ChannelType` покрывает это.

### 6.7 Общие механизмы переключения и прослушивания каналов

- `/ch <id>` (алиас `/channel`) — переключить активный (в который пишешь по умолчанию) канал.
- `/ch toggle <id>` — включить/выключить **прослушивание** канала лично для себя (не видеть сообщения из него), независимо от глобального `enabled` в конфиге.
- Быстрая отправка в конкретный канал без переключения: префикс-шорткат (`shortcut` в конфиге канала), например `l:привет` или `!привет` для глобального — отправляет только в этот канал, не меняя активный.
- Tab-complete для `/ch` показывает только каналы, доступные игроку по правам и включённые в конфиге.

## 7. Метки (теги) каналов

- Дефолтные значения (перекрываемые в конфиге): `[G]` — глобальный, `[L]` — локальный, `[$]` — торговый, `[ЛС]` — личные сообщения.
- Метка и её цвет задаются per-channel в `channels.yml` (см. пример в 6.1, поле `tag`), поддерживается MiniMessage-разметка (`<green>`, HEX `<#55ff55>`, легаси `&a` — с авто-конвертацией легаси-кодов в MiniMessage при парсинге конфига для удобства администраторов, привыкших к старому формату).
- Метка ЛС дополнительно варьируется по направлению: например `[ЛС →]` для исходящих и `[ЛС ←]` для входящих (настраиваемо, необязательно).

## 8. Настройка цвета префикса / никнейма / сообщения

Три независимых «цветовых слоя» на каждое сообщение:

1. **Цвет префикса** (то, что обычно приходит из LuckPerms `prefix`, но именно *цвет применения* этого текста настраивается отдельно от самого текста префикса).
2. **Цвет никнейма** игрока.
3. **Цвет текста сообщения**.

### 8.1 Приоритет разрешения цвета (сверху вниз — более высокий приоритет)

1. Индивидуальная настройка игрока через команду плагина (если есть право `unichat.color.self`) — хранится в `PlayerDataStore`.
2. Настройка группы через LuckPerms meta (`unichat-prefix-color`, `unichat-name-color`, `unichat-message-color`) — задаёт админ через `/lp group vip meta set unichat-name-color "<#55ffff>"`.
3. Дефолтный цвет канала из `channels.yml` (`format` шаблон уже может фиксировать цвет, если админ не хочет вариативности).
4. Глобальный дефолт из `config.yml`.

### 8.2 Команды для игрока (если разрешено правами)

- `/chatcolor name <цвет>` / `/chatcolor prefix <цвет>` / `/chatcolor message <цвет>` — установить свой цвет.
- `/chatcolor reset [name|prefix|message]` — сброс к цвету, определённому группой/каналом.
- `/chatcolor menu` — (Phase 3, опционально) chest-GUI с палитрой цветов для донат-групп, включая HEX-палитру/градиенты, если есть право.

### 8.3 Градация доступа к типам цвета (важная фишка для донат-серверов)

- `unichat.color.basic` — 16 стандартных цветов Minecraft.
- `unichat.color.hex` — произвольный HEX (`#RRGGBB`).
- `unichat.color.gradient` — градиенты через MiniMessage `<gradient:#c0ffee:#ff6a00>текст</gradient>` внутри имени/сообщения.
- `unichat.color.rainbow` / анимированные цвета — явно отметить как **nice-to-have**, не в MVP (см. Roadmap, Phase 4), из-за сложности (анимация текста в чате технически ограничена — обычно эмулируется покадровой рассылкой заново отрендеренного сообщения, что дорого; решение — не делать «живую» анимацию, а один раз применить радужный градиент к тексту при отправке).
- Все вводимые игроком цвета должны валидироваться и мимикрирующие санитайз-фильтром (нельзя внедрить произвольные MiniMessage-теги типа `<click>`/`<hover>` через цветовую команду — только цветовые теги whitelisted).

| `/unmute <игрок> [канал]` | | Размут | `unichat.mute` |

## 10. Права (permissions, ключевые узлы)

- `unichat.*` — все права (для OP/владельца).
- `unichat.channel.<id>.speak` / `unichat.channel.<id>.see` — писать/видеть конкретный канал.
- `unichat.channel.use` — базовое использование `/ch`.
- `unichat.color.self`, `unichat.color.basic`, `unichat.color.hex`, `unichat.color.gradient`.
- `unichat.pm.send`, `unichat.ignore`, `unichat.socialspy`.
- `unichat.mute`, `unichat.clear`, `unichat.pause`, `unichat.me`.
- `unichat.item.share` — использование токенов `*saleN` для показа предмета из хотбара в чате; `unichat.bypass.itemlinklimit` — снятие лимита `max-per-message`.
- `unichat.bypass.cooldown`, `unichat.bypass.filter`, `unichat.bypass.caps`, `unichat.bypass.mute`.
- `unichat.admin.reload`, `unichat.admin.debug`.

Все узлы регистрировать в `plugin.yml`/через `PluginManager#addPermission` с описаниями и дефолтными значениями (`op`/`true`/`false`), чтобы права были видны в `/lp editor` без ручного описания админом.

## 11. Модерация и антиспам

Функции, вдохновлённые ChatControl/VentureChat — обязательны к покрытию концептуально, глубина реализации по фазам (раздел 19):

- **Cooldown** — глобальный и per-channel лимит частоты сообщений.
- **Anti-flood / похожие сообщения** — блокировка повторной отправки идентичного/похожего (% сходства, порог настраиваемый) сообщения подряд.
- **Anti-caps** — если доля заглавных букв в сообщении выше порога (%), автоматически привести к нижнему регистру или отклонить с предупреждением (порог и длина минимального сообщения для проверки — настраиваемые).
- **Anti-advertising / фильтр ссылок** — регулярка на IP/домены/инвайты, whitelist доменов, действие: блокировать / заменять / только предупреждать (лог для админов).
- **Swear-filter (фильтр мата)** — список слов/regex с wildcard, замена на `***`, либо полный блок сообщения + уведомление модераторам.
- **Mute-система** — per-player, с TTL (временный мут), опционально per-channel (замьютить только в Trade, оставив Global), причина, история мутов (для `/mutehistory`, Phase 3).
- **Ignore-система** — как в 6.5, применимо и к обычным каналам, не только ЛС (по желанию администратора — конфиг-флаг).
- **Spy-режим** — стафф видит сообщения из отключённых у себя каналов / ЛС других игроков (см. 6.5) и видит игроков в vanish, если у спай-моды есть право.
- **Chat freeze / slowmode** — `/chatpause` замораживает весь чат кроме стаффа (для ивентов/раздач), `/slowmode <секунды>` временно повышает cooldown всем без права bypass.
- **Логирование чата** — опциональная запись всех сообщений (по каналам) в файл с ротацией по дням, для последующего аудита модераторами; включается флагом в конфиге (учитывать приватность — четко задокументировать, что логируется).

## 12. Дополнительные «фишки» (из анализа конкурентов)

### 12.1 JSON-интерактивность (hover/click)

- Наведение на никнейм в чате показывает hover-подсказку: ранг (LuckPerms group display name), онлайн-время, (опционально) баланс Vault.
- Клик по никнейму → подставляет в чат-инпут `/msg <ник> `.
- Автоопределение URL в сообщении → делает ссылку кликабельной (`open_url`) с явным подтверждением (Minecraft сам показывает диалог подтверждения при клике на непроверенную ссылку — этого достаточно, доп. капчу не делать).

### 12.2 Упоминания (mentions)

- `@nick` в сообщении подсвечивается отдельным цветом и (если упомянутый онлайн и видит канал) проигрывает звук уведомления (`Player#playSound`, настраиваемый звук/громкость, можно выключить лично через `/chatcolor` или отдельный тоггл `/mentions toggle`).
- Tab-complete для `@` — подсказывает ники игроков, видимых в текущем канале (для локального — только тех, кто в радиусе).

### 12.3 RP/утилитарные команды

- `/me <текст>` — действие в третьем лице (`* Игрок делает что-то`).
- Спойлер-тег в сообщении `||текст||` → скрыт, показывается по клику (Phase 3+, опционально).

### 12.4 Chat bubbles (пузыри чата над головой)

- Через Display Entities / TextDisplay (Paper 1.19.4+) поверх головы игрока на короткое время при отправке сообщения. Явно отметить как **Phase 4 / nice-to-have** — красивая, но не критичная фича, требует аккуратной работы с рендер-дистанцией и очисткой сущностей.

### 12.5 Прочее

- `/chatlog` (для стаффа) — открыть последние N сообщений выбранного игрока/канала в виде книги (`Book` через Adventure) для расследований.
- Плейсхолдер-хук для будущей интеграции автоперевода сообщений (не реализовывать сам перевод — просто не блокировать архитектурой).

### 12.6 Показ предмета из хотбара в чате (`*saleN`)

Функция-аналог ванильного «Shift+клик по предмету → вставить в чат», но через текстовый токен прямо в сообщении — удобно для торгового чата (показать зачарованную книгу, оружие, блок и т.д. вместе с текстом объявления), а не только целым отдельным сообщением.

**Синтаксис.** Игрок пишет в любом канале, например: `Продаю *sale1 и *sale3, торг уместен`. Токены `*sale1` … `*sale9` ссылаются на слоты хотбара 1–9 (слот 1 = крайний левый слот хотбара, слот 9 = крайний правый; внутренне это `PlayerInventory` слоты `0..8`).

- Ключевое слово `sale` — **настраиваемое** (`item-link.keyword` в `config.yml`, дефолт `sale`), т.к. механизм по сути общий («прикрепить предмет из хотбара»), а не только для продажи. Формат токена регэкспом: `\*<keyword>([1-9])`, регистронезависимо.
- Обработка происходит на этапе перехвата `AsyncChatEvent` **до** финального рендера сообщения:
  1. Найти в сыром тексте сообщения все вхождения токенов (максимум `item-link.max-per-message` штук, по умолчанию 5 — защита от раздувания пакета/спама).
  2. Для каждого токена проверить право `unichat.item.share`. Нет права → поведение по `item-link.no-permission-behavior`: `keep-text` (оставить `*sale1` как обычный текст, по умолчанию), `strip` (вырезать токен) или `block-message` (отменить отправку сообщения целиком с приватным предупреждением автору).
  3. Определить `ItemStack` в соответствующем слоте хотбара **на момент отправки** сообщения (важно: не хранить ссылку на сам объект, а сделать snapshot/clone, чтобы последующее изменение инвентаря игроком не повлияло на уже отправленное сообщение).
  4. Пустой слот → заменить на `item-link.empty-slot-text` (дефолт `<gray><пусто></gray>`), либо, если `item-link.block-if-empty: true`, отменить отправку с предупреждением (по умолчанию `false` — просто показываем «пусто» и отправляем остальной текст).
  5. Слот занят → собрать компонент-иконку: видимый текст вида `[Название предмета]` (имя — `displayName()` предмета, если задано кастомное, иначе локализованное/дефолтное; цвет скобок/текста — по редкости предмета, как в ванильной подсветке: обычный — белый, зачарованный/уникальный — light purple/фиолетовый, кастомное имя — курсив; переопределяется конфигом `item-link.display-color`), и **hover-событие `HoverEvent.showItem(...)`** (Adventure API) с полным материалом, количеством и NBT/`DataComponents` предмета.
  6. Заменить токен на собранный компонент в финальном сообщении, которое дальше проходит через обычный `FormatEngine` (раздел 4) вместе с остальными плейсхолдерами канала.
- **Зачарованные книги и энчанты** — специальной логики парсинга зачарований писать не требуется: если в `ShowItem`-событие корректно передать NBT/компоненты предмета «как есть» (через `BinaryTagHolder`/`DataComponentPatch` — в зависимости от версии Adventure/Paper API, актуальной на момент разработки), клиент Minecraft сам отрисует полный тултип с зачарованиями, лором и т.д. — как при обычном наведении в инвентаре.
- **Область действия.** Работает во всех каналах, где явно разрешено — переключатель есть и глобальный (`item-link.enabled`), и per-channel (`channels.<id>.item-link: true|false`), т.к. администратор может, например, разрешить показ предметов только в Trade и Local, но не в Global/ЛС.
- **Антиспам.** На сообщения с токенами действуют общие cooldown/антиспам-правила канала (раздел 11); отдельного лимита по времени на сам показ предмета не требуется, только лимит количества токенов в одном сообщении (`max-per-message`) и, опционально, право-бридж `unichat.bypass.itemlinklimit` для стаффа/донатов.
- **Валидация.** Токен, ссылающийся на несуществующий слот (например, `*sale0` или `*sale99`), не распознаётся регэкспом и остаётся обычным текстом — никакой отдельной обработки ошибок не требуется.
- **Задел на будущее (зафиксировать как открытый вопрос / nice-to-have, не в MVP этой фичи):** аналогичные токены для всего инвентаря и оффхенда (например `*inv10`…`*inv36`, `*offhand`), а также алиас `*hand` на предмет в текущей активной руке игрока.

## 13. Хранение данных

- **По умолчанию:** YAML-файлы на игрока (`playerdata/<uuid>.yml`) — активный канал, отключённые каналы, персональные цвета, список игнора, состояние мута/до какого времени.
- **Опционально (флаг в config.yml `storage.type: yaml|sqlite|mysql`):**
  - SQLite — локальная файловая БД, если нужна прозрачная работа с большим количеством записей (историй мутов, чат-логов) без внешнего сервера.
  - MySQL через HikariCP — для серверов, планирующих сеть (BungeeCord/Velocity) в будущем, чтобы данные игрока были доступны с разных бекендов.
- Схему миграции БД версионировать (простая таблица `schema_version`), чтобы обновления плагина не ломали существующие данные.

## 16. Нефункциональные требования (производительность, надёжность)

- Все интеграции — **мягкие зависимости** (`softdepend` в `plugin.yml`), отсутствие любой не приводит к ошибкам при старте (проверять `getServer().getPluginManager().getPlugin("X") != null` + try/catch вокруг регистрации хуков).
- Тяжёлые операции (запросы к БД, чтение/запись YAML игрока) — асинхронно, не блокировать основной поток тика сервера.
- Обработка чата — через **`io.papermc.paper.event.player.AsyncChatEvent`** (не deprecated `AsyncPlayerChatEvent`), финальный рендер через Adventure `Component`.
- Расчёт получателей локального чата — эффективный (не наивный полный обход онлайн-игроков с тяжёлыми вычислениями на каждое сообщение при высоком онлайне; использовать чанковые/пространственные выборки Paper API).
- Код бизнес-логики не должен напрямую держать глобальные мутабельные Map без синхронизации, если к ним возможен доступ из разных потоков (async БД + основной поток) — использовать `ConcurrentHashMap`/явную синхронизацию, чтобы в будущем не переписывать всё под Folia region-threading.
- Плагин не должен течь памятью: отписываться от слушателей LuckPerms/PAPI при `onDisable`, очищать данные вышедших офлайн-игроков из кешей.

## 17. Критерии приёмки (Definition of Done для MVP)

- [ ] Плагин собирается и запускается на чистом Paper 1.20.4+/1.21+ без установленных LuckPerms/Vault/PAPI — без ошибок в консоли, базовый чат работает.
- [ ] С установленными LuckPerms и Vault — префикс/суффикс подтягиваются, цвет по группе применяется без релога после изменения meta.
- [ ] Все 4 канала (Global/Local/Trade/PM) работают, каждый независимо включается/выключается в конфиге, при выключении не ломает остальные.
- [ ] Локальный чат по умолчанию ограничен 200 блоками, значение меняется в конфиге и применяется без перезапуска сервера (`/unichat reload`).
- [ ] Метки `[G]`, `[L]`, `[$]`, `[ЛС]` отображаются, тексты и цвета меток настраиваемы.
- [ ] Игрок с нужным правом может задать свой цвет префикса/ника/сообщения через команду, изменения сохраняются между заходами.
- [ ] Мут, игнор, антиспам-cooldown работают и не пропускают сообщения при превышении лимитов.
- [ ] PlaceholderAPI-экспаншен регистрируется и отдаёт корректные значения (если PAPI установлен).
- [ ] Токены `*sale1`…`*sale9` корректно заменяются на иконку предмета из соответствующего слота хотбара с рабочим hover-тултипом (включая зачарования у книг/предметов), пустой слот и отсутствие прав обрабатываются согласно конфигу.
- [ ] Нет дублирования сообщений в консоль/чат, нет исключений в логах при штатной работе (join/quit/chat/reload).

## 18. Roadmap (этапы реализации)

**Phase 0 — Скелет проекта**
Gradle-проект, `plugin.yml`, загрузка конфигов, определение установленных софт-депендов, логирование диагностики (`/unichat debug`).

**Phase 1 — MVP чата**
Global/Local/Trade/PM каналы, вкл/выкл в конфиге, метки, базовое форматирование, интеграция LuckPerms (прочтение prefix/suffix + свои meta-ключи цвета), Vault soft-depend (без экономических фич пока), радиус локального чата с дефолтом 200.

**Phase 2 — Цвета и модерация**
Команды `/chatcolor`, приоритеты разрешения цвета, права на HEX/градиент, мут/игнор/антиспам/anti-caps/swear-filter, `/socialspy`.

**Phase 3 — Расширенные фичи**
PlaceholderAPI-экспаншен полностью, JSON hover/click, показ предметов `*sale1`–`*sale9` (раздел 12.6), mentions+звук, `/me`, chat-log, chat pause/slowmode, GUI-палитра цветов (опционально).

**Phase 4 — Nice-to-have и подготовка к порту**
Chat bubbles, DiscordSRV-мост, WorldGuard региональные ограничения каналов, SQLite/MySQL storage backend, ревизия архитектуры на предмет абстракций для будущего порта на Spigot/Bukkit и адаптации под Folia.

## 19. Открытые вопросы (уточнить в процессе или зафиксировать дефолт и пойти дальше)

- Финальное имя плагина/пакет (`ru.<автор>.unichat` — заполнить).
- Нужен ли изначально билд под Folia-совместимость (частичная, без полноценного region-threading) уже в Phase 1, или это чисто Phase 4 — по умолчанию считаем, что архитектурная готовность закладывается сразу, а фактическая Folia-совместимость (`folia-supported: true` в `paper-plugin.yml`) — Phase 4.
- Нужна ли поддержка BungeeCord/Velocity-синхронизации каналов между серверами сети — по умолчанию **не в скоупе MVP**, но архитектура хранения данных (раздел 13) должна не мешать добавить это позже.
